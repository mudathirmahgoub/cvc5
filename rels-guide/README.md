# A guide to cvc5's relational solver

`theory_sets_rels_guide.pdf` (source `theory_sets_rels_guide.tex`) explains
`src/theory/sets/theory_sets_rels.{h,cpp}` for a newcomer:

* Part I  - the theory T_R and the CADE'17 calculus (Meng/Reynolds/Tinelli/Barrett)
* Part II - the data structures declared in the header, with lifetimes
* Part III- the algorithms in pseudocode, rule by rule, transitive closure in depth
* Part IV - the investigation: should `buildTCGraphForRel` be called once or twice?

Build with `pdflatex theory_sets_rels_guide.tex` (twice, for cross-references).

## Investigation outcome

Once, up front, immediately after `collectRelsInfo`. A later call overwrites
`d_tcr_tcGraph[tc_rel]` with a graph built from the base relation's members only,
discarding the closure edges `applyTCRule` had just added, which disables the
TCLOS UP II (transitivity) inference.

Implemented in commit `8bcdf3239` on branch `build-trc-graph-once`:
one unconditional pass over every `rel.tclosure` term at the top of `check()`,
both previous call sites deleted, `buildTCGraphForRel` no longer inserting empty
entries into the membership maps via `operator[]`, and
`regress0/rels/rel_tc_7.cvc.smt2` moved out of `regression_disabled_tests`.
`build-tc-graph-once.patch` is the original standalone patch against
`8dd659a3a`, kept for reference.

## Three configurations

The part compares three, and is careful about which one a claim is about:

| name        | commit                 | call sites                                     |
|-------------|------------------------|------------------------------------------------|
| _unguarded_ | `8dd659a3a`            | `applyTCRule` (guarded) + Phase B (no guard)   |
| _guarded_   | `c851f83bf` (PR #12793)| both, guarded on `d_rel_nodes`/`d_rRep_tcGraph`|
| _once_      | `8bcdf3239`            | one pass at the top of `check()`               |

PR #12793 fixed the same overwrite by guarding rather than by hoisting, so
against today's `main` this change is **behaviourally and performance-neutral**,
not a speedup. Its case is the invariant: "the graph is built once, before any
rule runs, and only added to afterwards", checkable by inspection.

## Benchmarks

Versus _unguarded_ (`main` when the investigation started):

    benchmarks/A-repro.smt2                  unguarded: timeout   once: unsat
    benchmarks/B-control-no-base-member.smt2 unguarded: unsat     once: unsat
    benchmarks/C-control-all-base.smt2       unguarded: unsat     once: unsat
    benchmarks/D-sat-no-path.smt2            unguarded: sat       once: sat
    benchmarks/E-chain4.smt2                 unguarded: timeout   once: unsat
    benchmarks/rel_tc_7.cvc.smt2             unguarded: timeout   once: unsat (0.01s)

Versus _guarded_ (`5cc03f4b9`), on 100 in-tree `rels` benchmarks plus the 67
generated by `gen_stress.py`:

    answers differing                                    0 / 167
    theory::sets inference histograms differing           0 / 167
    wall time, 67 generated benchmarks         8.663s vs 8.594s  (1.01x)
    ctest -R rels                                       99 / 99 pass
    ctest -R "sets|rels|relation"                      303 / 303 pass
    fuzz_tc.py, seeds 1-3, 900 instances vs oracle    900 / 900 both, 0 diffs

Half-merging the two fixes -- keeping the Phase B call site and dropping only
#12793's guard -- reproduces the original divergence on all four benchmarks
above that the overwrite affects. See "A merge hazard, measured".

## Scripts

* `benchmarks/gen_stress.py <outdir>` - the 67 scaling and equal-relation
  benchmarks used in Part IV.
* `benchmarks/compare.py a=<bin> b=<bin> <timeout> <files...>` - differential
  status and timing table; `REPS=n` for repeated runs (reports the minimum).
* `benchmarks/fuzz_tc.py <seed> <n>` - differential test against an exact
  reachability oracle. Point it at two snapshots with `BASE_BIN` / `ONCE_BIN`
  (see Appendix B of the PDF for why copying the executable alone is not
  enough); `MAX_NODES` / `MAX_EDGES` set the instance size.
